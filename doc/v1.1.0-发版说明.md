# v1.1.0 发版说明与操作清单

> 本文档记录 v1.1.0 的**签名密钥变更**这一重大变更、发版前必须完成的操作，
> 以及给用户的升级提示。发版后请保留本文件作为变更依据。

## ⚠️ 一、本次发版最重要的事：签名密钥已更换

### 发生了什么

| 项目 | 旧（v1.0.0 ~ v1.0.7） | 新（v1.1.0 起） |
|------|----------------------|----------------|
| 证书 DN | `CN=debumao` | `CN=debumao` |
| 证书 SHA-256 | `6C:1D:3F:27:19:AD:78:8C:80:C3:63:E3:E3:AD:49:C3:11:5A:A5:F4:0A:18:27:7A:7A:24:3D:36:80:6B:27:E2` | `B9:8A:E3:A9:F7:76:40:08:33:E6:5E:6B:03:9C:E3:5C:39:44:23:2D:89:DB:5E:35:E1:C6:24:9F:DA:B9:D4:4F` |
| 别名 | （未知） | `release` |
| 状态 | **密钥库文件已丢失**（仅存于 GitHub Secrets，无法导出） | 已备份至加密云盘 |

**原因**：v1.0.0 ~ v1.0.7 使用的密钥库文件未纳入有效备份（云盘中备份的是另一把同名密钥），
原文件已无法找回，故换用新密钥库。

### 对用户的影响（必须在 Release 说明中告知）

新版本的签名与旧版**不匹配**，Android 会拒绝覆盖安装并报：

```
INSTALL_FAILED_UPDATE_INCOMPATIBLE: Existing package cn.debubu.signalinsight
signatures do not match newer version; ignoring!
```

**此错误已在真机复现确认**（非推测）。

用户必须：
1. **先卸载**旧版本
2. 再安装 v1.1.0

> **副作用**：卸载会清除应用数据，即主题配色、刷新间隔等设置会恢复默认。
> 信号监测本身不留存历史数据，因此不会丢失监测记录。

### 版本号选择理由

从 `1.0.7` 跳到 **`1.1.0`**（而非 `1.0.8`）：
沿用同一 `versionCode` 序列（7 → 8）但次版本号递增，让签名不兼容这一**破坏性变更**
在版本号上就能被识别，避免与 v1.0.x 混淆。

## 二、发版前必须完成的操作

### 步骤 1：更新 GitHub Secrets（**必做，否则 CI 构建的包签名错误**）

进入仓库 → `Settings` → `Secrets and variables` → `Actions`，更新以下 4 个 Secret：

| Secret 名称 | 应填入的值 |
|-------------|-----------|
| `SIGNING_KEY` | `private-release.jks` 的 **Base64 编码**（见下） |
| `KEY_STORE_PASSWORD` | 见 `private-keystore.properties` 的 `storePassword` |
| `KEY_PASSWORD` | 见 `private-keystore.properties` 的 `keyPassword` |
| `KEY_ALIAS` | `release` |

**生成 Base64**：

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("private-release.jks")) | Set-Clipboard
```

然后直接粘贴到 `SIGNING_KEY` 的值里（**不要有多余换行**）。

> CI 中 `KEY_ALIAS` 若仍是旧值会导致签名失败——旧密钥的别名与新密钥（`release`）不一定相同，
> **务必一并更新**。

### 步骤 2：自动触发已恢复

`.github/workflows/release.yml` 中的 `on.push.tags` **已恢复**（推送 `v*` tag 即自动发版）。
若日后需再次临时冻结发版，把该段注释掉即可（保留 `workflow_dispatch` 手动触发）。

**CI 兼容性已实测验证**（在干净 worktree 中完整复现 workflow 的三个关键步骤）：

| 验证项 | 结果 |
|--------|------|
| 干净 checkout 无私钥文件 | ✅ |
| 步骤「解码签名密钥」写入 `app/release.jks` | ✅ 2682 字节，与源文件一致 |
| 步骤「写入签名配置」生成 `keystore.properties` | ✅ |
| 密钥库路径解析（`storeFile=release.jks`，文件在 `app/`） | ✅ 正确回落，未误判 |
| `./gradlew assembleRelease` | ✅ BUILD SUCCESSFUL |
| **产物签名指纹** | ✅ `b98ae3a9…d44f`，与新密钥一致 |

> 该验证排除了一个隐患：`app/build.gradle.kts` 在 v1.1.0 中新增了密钥库路径解析逻辑
> （优先项目根目录、回落 app 模块目录），CI 的密钥位于 `app/` 下，已验证能正确解析。

### 步骤 3：构建并验证签名（本地或 CI 产物都要验）

```powershell
# 本地构建
./gradlew assembleRelease

# 验证签名指纹 —— 必须输出 b98ae3a9...d44f
& "$env:ANDROID_HOME\build-tools\37.0.0\apksigner.bat" verify --print-certs `
    app\build\outputs\apk\release\SignalInsight-v1.1.0-release.apk |
    Select-String "SHA-256 digest"
```

**期望输出**：

```
V2 Signer: certificate SHA-256 digest: b98ae3a9f776400833e65e6b039ce35c3944232d89db5e35e1c6249fdab9d44f
```

### 步骤 4：打 tag 并发布

```bash
git tag -a v1.1.0 -m "v1.1.0"
git push origin v1.1.0
```

## 四、以后如何避免同样的问题

**教训**：密钥库文件当时只备份了一份，且备份的是**另一把同名密钥**，导致真正在用的密钥无备份。

### 建议做法

1. **备份后立即验证**，而不是只看文件存在：
   ```powershell
   keytool -list -v -keystore 备份的.jks -storepass 密码 | Select-String SHA256
   ```
   指纹必须与**线上 APK 实测指纹**一致，才算备份有效。

2. **核对线上包指纹的方法**（任何时候都可验证备份是否就是发版用的密钥）：
   ```powershell
   # 下载任一线上 release APK,读它的签名指纹
   & apksigner.bat verify --print-certs 线上的.apk | Select-String "SHA-256 digest"
   ```
   与本地密钥库的 `keytool ... | Select-String SHA256` 输出**逐位比对**。

3. **多处备份**：加密云盘 + 密码管理器附件 + 离线介质，至少两处。

4. **密钥库只生成一次**，不要因为"再生成一个更规范的"而重复创建同名密钥——
   本次问题很可能就源于当天先后生成过两把 `CN=debumao` 的密钥。

5. **记录指纹**：把当前生效的密钥指纹写入项目文档（本文件与 `agents.md` 已记录），
   下次备份时可随时核对。
