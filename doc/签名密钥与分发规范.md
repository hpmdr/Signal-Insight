# 签名密钥说明与分发规范

> 本文档取代原 `doc/v1.1.0-发版说明.md` 中关于「密钥丢失」的错误结论。
> 编写依据：对线上 8 个 Release 包逐一提取证书指纹的实测结果。

---

## 一、结论先行

**分发一律走 GitHub Release（CI 构建）。不要用本地 `assembleRelease` 的产物对外分发。**

原因：**本地能拿到的密钥，与线上在用的密钥，不是同一把。**

| 密钥 | 证书 SHA-256 | 存放位置 | 用途 |
|------|-------------|---------|------|
| **A（线上真身）** | `6C:1D:3F:27:19:AD:78:8C:80:C3:63:E3:E3:AD:49:C3:11:5A:A5:F4:0A:18:27:7A:7A:24:3D:36:80:6B:27:E2` | **仅 GitHub Secrets** | ✅ 正式发布（CI 使用） |
| **B（本地持有的）** | `B9:8A:E3:A9:F7:76:40:08:33:E6:5E:6B:03:9C:E3:5C:39:44:23:2D:89:DB:5E:35:E1:C6:24:9F:DA:B9:D4:4F` | `private-release.jks`（别名 `release`） | ⚠️ 仅本地验证，**不可分发** |
| **C（公开测试）** | `1E:38:27:E8:DE:02:AA:B8:F6:C0:E3:3B:2D:AB:73:04:8F:63:04:86:C7:B3:16:68:41:B4:1B:01:39:0F:D0:2F` | `app/signal_insight.jks`（密码 `Android123`，**有意公开**） | 开发者本地调试 |

> A 与 B 的**证书 DN 都是 `CN=debumao`**，但指纹不同 —— 是两把不同的密钥。

---

## 二、实测依据

对 GitHub 上全部 Release 包提取签名证书（用 `apksigner` 与手工解析 APK Signing Block 两种方式交叉验证）：

| 版本 | 证书 SHA-256 | 公钥 SHA-256 |
|------|-------------|-------------|
| v1.0.0 | `6c1d3f27…b27e2` | `49f6bbe6…0d6f` |
| v1.0.1 ~ v1.0.6 | 同上 | 同上 |
| v1.0.7 | 同上 | 同上 |
| **v1.1.0（CI 构建）** | 同上 | 同上 |

**八个版本指纹完全一致** → 说明 GitHub Secrets 中的密钥从 v1.0.0 起从未变更，且一直工作正常。

而本地用 `private-release.jks` 签出的包为：

| 构建来源 | 证书 SHA-256 | 公钥 SHA-256 |
|---------|-------------|-------------|
| 本地 `assembleRelease` | `b98ae3a9…d44f` | `d0017675…3fea` |

**公钥不同 ⇒ 私钥必然不同**（公钥由私钥数学推导，无法伪造）。

---

## 三、为什么会这样

### GitHub Secrets 的工作方式

Secrets **不是每次打 tag 上传的产物，而是一次性配置、长期保存的凭据**：

```
（某时间点）手动在网页上传密钥 A → 存入 Secrets（加密保存）
                                        ↓
每次打 tag → workflow 用 ${{ secrets.SIGNING_KEY }} 读取 → 解码 → 签名 → 上传 APK
```

workflow 中只有**读取**动作，没有任何上传密钥的步骤：

```yaml
- name: 解码签名密钥
  env:
    KEYSTORE_BASE64: ${{ secrets.SIGNING_KEY }}   # 读取已存的 Secret
  run: echo "$KEYSTORE_BASE64" | base64 --decode > app/release.jks
```

因此：**只要 Secrets 不被手动修改，每次发版用的都是同一把密钥。**

### 本地那把（B）从何而来

推测：在配置线上密钥前后，本地曾生成过两把 `CN=debumao` 的密钥；备份到云盘的是**未被线上采用的那一把**。

时间线参考：

```
2026-06-15 10:36   CI 发布 v1.0.0  ← 此时密钥 A 已在 Secrets 中就位
2026-06-15 16:33   本地密钥 B 的创建时间（比 v1.0.0 发布晚约 6 小时）
```

即 **v1.0.0 发布时，密钥 B 尚未存在**，线上不可能是用它签的。

## 四、当前风险与建议

### ⚠️ 风险：密钥 A 没有文件备份

密钥 A **只存在于 GitHub Secrets**。GitHub Secrets 是**只写不读**的（界面与 API 都不返回值），
因此**无法把 A 导出到本地**。同时，**私钥无法从已发布的 APK 反推**。

这意味着：

- 只要 GitHub 账号与 Secrets 完好 → 发版不受影响 ✅
- 若 Secrets 被误删 / 账号异常 → 将永久失去线上签名能力，届时只能换密钥并让用户重装

### 建议

1. **不要修改 Secrets 里的 `SIGNING_KEY` / `KEY_ALIAS` 等值**（当前值已验证可用）
2. **谨慎对待 Secrets 的删除操作**——GitHub 不提供回收站
3. 若希望获得「可备份、可本地签名」的密钥，需要主动做一次**换密钥**：
   - 把 Secrets 更新为密钥 B（`private-release.jks`）
   - 代价：已安装用户必须**卸载重装**（签名不匹配），且会丢失主题与刷新设置
   - 收益：从此 CI 与本地签名一致，且密钥有云盘备份
   - **是否做这笔交易由维护者决定**；若线上用户很少，成本可控

## 五、防呆措施（已实施）

`app/build.gradle.kts` 在本地用密钥 B 构建 release 时会打印醒目警告：

```
========================================================================
警告: 正在使用「本地密钥」,签出的 APK 无法覆盖线上版本!
  本次签名证书指纹: B9:8A:E3:A9:...:D4:4F
  线上发布的指纹  : 6C:1D:3F:27:...:27:E2
  两者不同 -> 该 APK 与 GitHub Release 上的包签名不匹配,
  用户安装时会报 INSTALL_FAILED_UPDATE_INCOMPATIBLE。
  正式分发请一律走 GitHub Release（由 CI 用 Secrets 中的密钥签名）。
  本地 assembleRelease 仅用于验证编译 / 混淆结果。
========================================================================
```

### 如何核对任意一个包用的是哪把密钥

```powershell
# 看包（APK）
& "$env:ANDROID_HOME\build-tools\37.0.0\apksigner.bat" verify --print-certs 某.apk |
    Select-String "SHA-256 digest"

# 看本地密钥库
keytool -list -v -keystore private-release.jks | Select-String SHA256
```

**指纹与线上一致（`6C:1D:3F:27…`）才可分发。**

## 六、发版流程（标准）

```bash
# 1. 确认版本号（app/build.gradle.kts 的 versionCode / versionName）
# 2. 推送到 master
git push origin master

# 3. 打 tag 并推送（触发 CI 自动构建 + 发布）
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

CI 会自动：校验 SDK 组件 → 读取 Secrets 中的密钥 → 构建签名 APK → 创建 GitHub Release。

**发布后建议核对一次签名指纹**（见第五节），确认与线上一致。
